# iOS Safari / WebKit JS, animation, media and performance pitfalls (2024-2026) for an animated marketing site

Research method note: web search results were used throughout. Direct page fetches of gsap.com, bugs.webkit.org and similar hosts were blocked by the sandbox egress proxy (CONNECT 403), so findings below rest on search-engine extracts of those pages, not full reads. Everything from general engineering knowledge that I could not re-verify in this session is placed under "Inferences" and labelled as such.

Site stack considered: GSAP 3 + ScrollTrigger + SplitText "films" (30 s timelines started by IntersectionObserver at threshold 0.35-0.6, paused out of view), `gsap.ticker.lagSmoothing(500, 33)`, Lenis only on `(pointer:fine)`; three.js GLB iPhone on a phone-sized canvas that copies a CSS 3D transform every frame, pixel ratio 1.5 on coarse pointers (1 while moving); Web Audio synth sounds; IO-driven chat animation with `setTimeout` chains; CSS keyframe entrances at first paint; a demo site in a transform-scaled iframe; the whole site also previewed inside a cross-origin claude.ai iframe on iPhone; webp + srcset images; multi-MB 3D model.

## 1. Frame-rate throttling (Low Power Mode, background, cross-origin iframes), GSAP behaviour, ScrollTrigger on iOS, IntersectionObserver quirks

### Takeaway
On iPhone the animation clock is not guaranteed 60/120 fps: Low Power Mode caps `requestAnimationFrame` at ~30 fps by design, hidden tabs stop rAF, and any cross-origin iframe that has not yet been tapped (exactly the claude.ai preview case) has both rAF and DOM timers throttled to ~30 fps, with taps not always clearing it. ScrollTrigger's main iOS issue is the address bar show/hide resize; `ScrollTrigger.config({ ignoreMobileResize: true })` is the low-risk fix, while `normalizeScroll(true)` is an "experimental" heavier fix with known trade-offs (momentum kill, swiping over links).

### Cited Findings
- WebKit throttles rAF to 30 fps when iOS Low Power Mode is on (changeset r213169); in WebKit bug 215745 a WebKit engineer said the 30 fps cap is intentional and that iOS 13's uncapped behaviour was the bug — [WebKit bug 215745](https://bugs.webkit.org/show_bug.cgi?id=215745)
- iOS 13 regression: in Low Power Mode rAF was observed at ~90 Hz, suspected to be a 30 Hz timer added while the old 60 Hz timer was not cancelled — [WebKit bug 202269](https://www2.webkit.org/show_bug.cgi?id=202269)
- Background on when iOS throttles rAF to 30 fps (Low Power Mode, cross-origin iframes) — [Popmotion blog](https://popmotion.io/blog/20180104-when-ios-throttles-requestanimationframe); also [Motion magazine: when browsers throttle rAF](https://motion.dev/magazine/when-browsers-throttle-requestanimationframe)
- GSAP forum: no sanctioned way to keep GSAP at 60 fps in Low Power Mode; responder's advice is that the device is purposefully lowering FPS to save battery and you should respect it — [GSAP forum 26826](https://greensock.com/forums/topic/26826-any-way-to-keep-gsap-running-at-60fps-while-mobile-device-is-in-low-power-mode/)
- A GSAP forum thread specifically reports persistent ScrollTrigger problems on iPhone in battery-save mode — [GSAP forum 39457](https://gsap.com/community/forums/topic/39457-persistent-issue-with-gsap-scroll-trigger-on-iphone-in-battery-save-mode/) (thread contents not readable in this session)
- WebKit changeset 215070 (April 2017, Simon Fraser, bug 170534) throttles rAF to 30 fps in cross-origin iframes that have never seen a user interaction ("NonInteractedCrossOriginFrame"), cleared when interaction is detected in that frame or a child frame — [trac.webkit.org r215070](https://trac.webkit.org/r215070)
- Companion change (changeset 215116, bug 170613) applies the same throttling to DOM timers (setTimeout/setInterval) in non-interacted cross-origin iframes — [trac.webkit.org r215116](https://trac.webkit.org/projects/webkit/changeset/215116?format=zip)
- WebKit bug 213344 (2020): mouse interaction lifts the throttle but a quick tap on a cross-domain iframe may not; a developer also reports a touch swipe does not count as interaction and that synthetic interactions do not bypass the throttle — [WebKit bug 213344](https://bugs.webkit.org/show_bug.cgi?id=213344); [Adobe community thread](https://community.adobe.com/t5/animate-discussions/iframe-plays-html-canvas-animations-slower-in-safari/m-p/9617872/highlight/true)
- GreenSock staff: iOS Safari throttles updates in non-activated iframes, affecting rAF and setTimeout alike, unrelated to GSAP; only workaround known was a "click here" overlay to get the user to activate the iframe (2020 thread) — [GSAP forum 25666 iframe throttling iOS](https://greensock.com/forums/topic/25666-iframe-throttling-ios/)
- GSAP ticker docs: when the tab is hidden the ticker slows sharply because the browser throttles rAF; `lagSmoothing(threshold, adjustedLag)` adjusts timing when the CPU falls behind; setting `lagSmoothing(0)` disables it app-wide — [gsap.ticker docs](https://gsap.com/docs/v3/GSAP/gsap.ticker/)
- `ScrollTrigger.normalizeScroll(true)` moves scrolling onto the JS thread and prevents the address bar show/hide on most devices, except the most recent iOS on phones in portrait, where GSAP says it seems impossible to work around — [GSAP docs normalizeScroll](https://gsap.com/docs/v3/Plugins/ScrollTrigger/static.normalizeScroll()); [GSAP 3.10 blog](https://www.gsap.com/blog/3-10/)
- `ScrollTrigger.config({ ignoreMobileResize: true })`: vertical-only resizes (~25% of viewport height) on touch-only devices no longer trigger `ScrollTrigger.refresh()`; start/end positions may be slightly inaccurate, which GSAP says is often preferable to visual jumps — [GSAP docs](https://gsap.com/docs/v3/Plugins/ScrollTrigger/static.normalizeScroll()); [GSAP forum 35475](https://greensock.com/forums/topic/35475-scrolltriggerscrollsmoother-normalizescroll-ignoremobileresize/)
- normalizeScroll trade-offs: GreenSock calls it "not a silver bullet... somewhat experimental"; it fixes iOS jitter but "can be more demanding on the processor" and is "definitely not something we recommend using for everything" — [GSAP forum 31763](https://greensock.com/forums/topic/31763-scrollsmoother-safari-issue-related-to-scrollsmoother-normalizescroll/)
- normalizeScroll side effects reported: swiping over `<a>` links opens the link instead of scrolling (Rodrigo: "there are tradeoffs unfortunately") — [GSAP forum 40874](https://gsap.com/community/forums/topic/40874-gsap-normalizescrolltrue-makes-it-impossible-to-scroll-through-the-link-areas-on-mobile-devices); momentum killed after overscrolling at page bottom on iOS Safari — [GSAP forum 45397](https://gsap.com/community/forums/topic/45397-normalizescroll-momentum-killed-after-attempting-to-scroll-past-page-bottom-ios-safari/); not working on some iOS devices — [GSAP forum 36502](https://gsap.com/community/forums/topic/36502-scrolltriggernormalizescroll-doesnt-work-on-some-ios-devices/)
- GSAP 3.11.5: normalizeScroll now auto-cancels its momentum scroll on mobile when something else changes scroll or on touchmove — [GSAP 3.11.5 release](https://github.com/greensock/GSAP/releases/tag/3.11.5)
- IntersectionObserver shipped in WebKit for iOS 12.2 — [WebKit blog: IntersectionObserver in WebKit](https://webkit.org/blog/8582/intersectionobserver-in-webkit/)
- IO spec: with `root: null` (implicit root) the root is the top-level browsing context's viewport, and targets may live in nested (including cross-origin) frames; margins/offsets are applied only to same-origin-domain targets and ignored for cross-origin ones — [W3C Intersection Observer (2023 WD)](https://www.w3.org/TR/2023/WD-intersection-observer-20231018); [w3c/IntersectionObserver #531](https://github.com/w3c/IntersectionObserver/issues/531)
- Practical report: rootMargin is only applied to the top-level container; an iframe acts as its own clipping container where rootMargin is not applied; workaround is an explicit-root observer inside the iframe — [toss/slash PR 283](https://github.com/toss/slash/pull/283)

### Inferences
Per-pitfall table for this site (fixes are my engineering recommendations derived from the findings above unless otherwise cited):

- P1 Low Power Mode 30 fps. Symptom: films and the 3D phone look "steppy"; scrubbed ScrollTrigger effects lag. Cause: rAF capped at 30 fps (by design). Detect without device: in a desktop browser, throttle rAF artificially (e.g. `gsap.ticker.fps(30)`) and view the site — this reproduces the cadence. Fix: accept 30 fps; avoid choreography that relies on per-frame smoothness of large moves (fast big translations look worst at 30 fps); prefer CSS transform/opacity tweens; keep `lagSmoothing(500,33)` (33 ms adjusted lag matches a 30 fps frame so a stall >500 ms pauses the film instead of jumping). Do not set `gsap.ticker.fps()` higher or try to defeat the cap.
- P2 Cross-origin claude.ai iframe preview. Symptom: on iPhone, everything animates at ~30 fps and the chat `setTimeout` chains run slow/jerky until the user taps; a scroll swipe alone may not "activate" the frame. Cause: WebKit NonInteractedCrossOriginFrame throttling of rAF and timers (r215070, r215116; tap gap in bug 213344). Detect: open the site inside any cross-origin iframe on a Mac Safari / iOS Simulator and compare fps with top-level; or log `performance.now()` deltas in a rAF loop. Fix: judge real smoothness only on the top-level URL, not the claude.ai preview; optionally show a "tap to start" affordance in the hero (the first tap also unlocks audio and loads the GLB, which the site already gates on first gesture), and drive the chat sequence from a GSAP timeline (`tl.call`, `gsap.delayedCall`) rather than raw `setTimeout`, so it shares one clock that pauses/resumes with the film and is subject to lagSmoothing.
- P3 Background tab / app switch. Symptom: returning to Safari, films resume oddly or `setTimeout` chat chains have fired in bulk. Cause: rAF stops in hidden tabs; timers are throttled; GSAP time is lag-smoothed but raw timers are not. Fix: pause films on `visibilitychange` (hidden) and resume on visible; put timers on the GSAP timeline (as P2).
- P4 Address bar resize. Symptom: ScrollTrigger positions jump / pinned sections twitch when the URL bar collapses. Cause: vertical viewport resize triggers `ScrollTrigger.refresh()`. Fix: `ScrollTrigger.config({ ignoreMobileResize: true })` (low risk); use `svh`/`lvh`/`dvh` CSS units consciously (general knowledge; svh for stable full-height sections). Use `normalizeScroll(true)` only if jitter persists, scoped to touch devices, and test link-swiping and bottom overscroll (known issues). Since Lenis is not used on touch, native momentum remains — keep it that way.
- P5 IntersectionObserver film triggers. Inside the cross-origin claude.ai iframe, the site's own IO (root null) is evaluated against the iframe's viewport, which is fine for thresholds, but any `rootMargin` on observers whose targets are cross-origin to the top document is ignored per spec; thresholds 0.35-0.6 on very tall film sections may never be reached on a short phone viewport (an element taller than ~1/0.6 of viewport height can never be 60% visible) — use `threshold` relative to a small sentinel element or compute with `intersectionRect.height / rootBounds.height` instead. This tall-element threshold trap is general IO behaviour, not iOS-specific, but it bites on phones because viewports are short. Transform-scaled demo iframe: IO inside the demo document measures against the demo's own (unscaled) viewport; to know whether the demo is on screen use an observer in the parent page on the iframe element.

- No source found confirming whether WebKit fixed the tap-does-not-unthrottle bug 213344 in iOS 17/18/26; status unknown.

## 2. WebGL / three.js on iOS: memory, context loss, canvas size, DPR 3, thermal; compositing layer memory and "A problem repeatedly occurred"

### Takeaway
The iOS "A problem repeatedly occurred on <site>" page is iOS killing the WebContent process for memory; heavy WebGL textures, multiple live canvases and too many compositing layers are the usual causes, and often no `webglcontextlost` fires before the kill. Keep one renderer, small textures (GPU memory is uncompressed RGBA unless using KTX2), capped DPR, render-on-demand, and handle `webglcontextlost` (iOS 17+ loses context on backgrounding in some versions).

### Cited Findings
- WebKit bug 290623 (March 2025): switching between two three.js pages on iPhone 13 mini, page memory climbed from ~180 MB to ~338 MB until "A problem repeatedly occured" / black screen; WebGL pages can exceed 500 MB when context is not lost on navigation — [WebKit bug 290623](https://bugs.webkit.org/show_bug.cgi?id=290623)
- WebKit bug 300782 (October 2025): iOS terminates heavy WebGL/texture pages for memory and Safari immediately reloads them, causing an endless reload loop until "A problem repeatedly occurred"; no out-of-memory error or `webglcontextlost` observed before termination — [WebKit bug 300782](https://bugs.webkit.org/show_bug.cgi?id=300782)
- react-three-fiber issue: each remount created a new WebGL2 canvas whose context was never lost; after a certain number of canvases Safari forced a reload — [pmndrs/react-three-fiber #3093](https://redirect.github.com/pmndrs/react-three-fiber/issues/3093)
- three.js forum (2025): Safari / any iOS browser crashes with WebGL, seen since 2021, user concludes it is a browser-side iOS issue — [three.js forum 81629](https://discourse.threejs.org/t/safari-any-web-browser-crash-on-iphone-when-use-webgl/81629); older reports — [Apple dev forums 662251](https://developer.apple.com/forums/thread/662251), [three.js #22582](https://github.com/mrdoob/three.js/issues/22582)
- Backgrounding Safari then returning causes WebGL context loss (reported from iOS/iPadOS 17 beta 8); a three.js maintainer says you must listen for `webglcontextrestored` and recreate all WebGL entities, and most three.js demos ignore context loss — [three.js forum 55772](https://discourse.threejs.org/t/context-lost-when-backgrounding-safari-on-ios-17-developer-beta-8/55772/4); [Apple dev forums 737042](https://developer.apple.com/forums/thread/737042); [WebKit bug 261331](https://bugs.webkit.org/show_bug.cgi?id=261331); still reported March 2025 — [WebKit bug 289601](https://bugs.webkit.org/show_bug.cgi?id=289601)
- Without `preventDefault()` in the `webglcontextlost` handler the browser will not attempt restoration — [MDN webglcontextrestored](https://www-igm.univ-mlv.fr/~forax/MDN/developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextrestored_event.html); [bugnet guide](https://bugnet.io/blog/fix-webgl-context-lost-on-tab-switch-restoration)
- Safari total canvas memory limit warning "(384 MB)" (iOS 15; lower on earlier versions, likely device-specific) — [PQINA: total canvas memory](https://www.pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/); [WebKit bug 195325](https://bugs.webkit.org/show_bug.cgi?id=195325); [Apple dev forums 687866](https://developer.apple.com/forums/thread/687866). A CanvasJS reply claims WebKit dropped canvas buffer memory from 448 MB to 224 MB — [canvasjs.com](https://canvasjs.com/?p=24273) (conflicting/older figure)
- Canvas area limit 16,777,216 px (width*height) in Safari ("Canvas area exceeds the maximum limit") — [PQINA: canvas area](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/); a 1600x1600 CSS canvas at DPR 3 becomes 4800x4800 and exceeds it — [Adobe community](https://community.adobe.com/t5/animate-discussions/canvas-dimensions-grow-with-higher-screen-density-gt-error/m-p/13664007)
- WebKit Web Inspector Layers tab: layers trade speed for memory, "Creating too many layers... can have disastrous results on memory-constrained devices"; Layers tab shows per-layer memory cost and the reason it was composited; "Show compositing borders" overlays layers and repaint counts — [WebKit Web Inspector Layers tab](https://webkit.org/web-inspector/layers-tab/)
- iOS 15.6 bug: compositing many z-indexed elements spiked memory >1 GB and reloaded the page (fixed) — [WebKit bug 243949](https://bugs.webkit.org/show_bug.cgi?id=243949); iOS 16.1 crash on pinch-zoom with a few `will-change: transform` elements, ~50 MB of compositing for three divs (open) — [WebKit bug 256876](https://www2.webkit.org/show_bug.cgi?id=256876); 2024 suggestion to watch total layer memory in Layers tab — [WebKit bug 276057](https://bugs.webkit.org/show_bug.cgi?id=276057)

### Inferences
- P6 Tab crash / reload loop ("A problem repeatedly occurred"). Symptom: page reloads on iPhone, sometimes repeatedly, often after the 3D phone appears or after scrolling through many animated sections. Cause: WebContent process exceeds iOS memory budget (WebGL textures + canvas backing stores + compositing layers + decoded images). Detect without device: Safari desktop Web Inspector Layers tab + Timelines "Memory" on macOS gives a proxy; Chrome DevTools "Layers" and `performance.memory` are Chromium-only proxies. On-device the only reliable tool is Web Inspector over USB from a Mac. Fix (three.js, general knowledge, consistent with findings): one `WebGLRenderer` for the page life, never recreate on re-entry; dispose geometries/materials/textures (`.dispose()`) when the model is permanently gone; compress GLB with Draco or meshopt and textures as KTX2/Basis (GPU stays compressed) or at least cap textures at 1024-2048 px — a 4096x4096 RGBA texture is ~64 MB uncompressed, ~85 MB with mipmaps (arithmetic: 4096*4096*4 bytes); `antialias: false` when DPR > 1; `powerPreference: 'low-power'` is acceptable for a single product model.
- P7 Pixel ratio and canvas size. DPR 3 on modern iPhones: a phone-sized canvas of e.g. 300x620 CSS px at DPR 1.5 is ~0.4 MP (cheap); at DPR 3 it would be ~1.7 MP and 4x the fill cost. The site's `setPixelRatio(Math.min(devicePixelRatio, 1.5))` on coarse pointers and 1 while moving is good; make sure `renderer.setSize` is not called every frame (it reallocates the drawing buffer) — only when the pixel ratio actually changes, and debounce the switch back to 1.5.
- P8 Rendering every frame while copying a CSS 3D transform. Symptom: phone gets warm, frame rate drops after ~1-2 minutes (thermal throttling), battery drain. Cause: continuous WebGL render even when nothing changes. Fix: render only when the copied transform matrix changed or an animation is running (dirty flag); stop the render loop when the canvas is off-screen (IO) or the tab is hidden; under Low Power Mode you get 30 fps anyway.
- P9 Context loss on backgrounding (iOS 17+). Symptom: returning to Safari shows a blank/black phone model. Fix: `canvas.addEventListener('webglcontextlost', e => { e.preventDefault(); stopLoop(); })` and on `webglcontextrestored` re-upload (three.js re-initialises its state on restore, but custom render targets/textures may need `needsUpdate = true`; worst case re-create renderer and reload the GLB from HTTP cache); show the CSS/PNG fallback phone meanwhile. Note `renderer.forceContextRestore()` only works after a programmatic `loseContext()`, so it does not help a real iOS loss (general knowledge, unverified in this session).
- P10 Compositing layers. Symptom: memory pressure, flicker, or crash with many animated elements, especially SplitText (each char/word wrapped in a span; if each gets `will-change` or a 3D transform, each becomes a layer). Fix: do not leave `will-change` on permanently; let GSAP use 2D transforms for split text (`force3D: "auto"` default drops the 3D matrix when tween ends); revert SplitText after the film finishes (`split.revert()`); avoid `preserve-3d` trees except the phone; check Layers tab count/memory.

### Gaps
- No official Apple number for per-tab memory budget on current iPhones (iOS 18/26); reports suggest crashes in the ~300-500+ MB range on an iPhone 13 mini, but this is device-specific and not documented.
- The current Safari canvas memory limit (384 MB vs 224 MB claims) is inconsistent across sources; unverified for iOS 18/26.
- Did not find three.js official docs/forum guidance specific to iOS DPR caps beyond community practice; three.js manual pages could not be fetched.
- No data found on thermal-throttling onset times for WebGL in Safari.

## 3. Web Audio on iOS: unlock, silent switch, "interrupted" state, reuse across buttons

### Takeaway
iOS treats Web Audio as "ambient" audio, so with the ringer/silent switch on, synthesized sounds are muted even after a correct gesture unlock; set `navigator.audioSession.type = 'playback'` where supported (feature-detect). The AudioContext can go to the non-standard "interrupted" state when the user leaves the page, locks the screen, or another tab plays audio; every button that plays sound must check `ctx.state` and call `resume()` synchronously inside its own click handler.

### Cited Findings
- MDN: in iOS Safari, when the user leaves the page (switches tabs, minimizes the browser, turns off the screen) the AudioContext state changes to "interrupted" and needs to be resumed; MDN's example checks the state and calls `audioCtx.resume().then(play)` — [MDN AudioContext.state (ja)](https://developer.mozilla.org/ja/docs/Web/API/AudioContext/state)
- WebKit bug reports: context stuck in "interrupted" on iPhone/iPad with `resume()` not working — [WebKit bug 273511](https://bugs.webkit.org/show_bug.cgi?id=273511); resume after returning to Safari could fail with a permission-style error while state still reported "running" — [WebKit bug 217606](https://bugs.webkit.org/show_bug.cgi?id=217606); "interrupted" is not a standard state (WebKit commenter) — same
- 2018 report: `resume()` after user interaction only produced sound if interaction was within ~5 s of page load — [WebKit bug 190410](https://bugs.webkit.org/show_bug.cgi?id=190410) (old; may be fixed)
- PlayCanvas: audio suspended after Safari minimized, a tap needed to resume — [PlayCanvas forum](https://forum.playcanvas.com/t/ios-audio-not-resuming-after-standby/26408)
- Common unlock pattern: one-time touch/mouse listeners that resume the context on the first gesture; iOS Safari prevents Web Audio playback when the ringer is set to vibrate/silent — [Matt Montag: Unlock Web Audio](https://www.mattmontag.com/?p=2295)
- Web Audio is "ambient" on iOS: mixes with other apps but obeys the mute switch; `<audio>`/`<video>` interrupt other audio and ignore the switch — [swevans/unmute](https://github.com/swevans/unmute); [Audjust: unmute Web Audio on iOS](https://www.audjust.com/blog/unmute-web-audio-on-ios)
- Setting `navigator.audioSession.type = 'playback'` (or 'play-and-record') stops silent-mode muting; feature-detect before using — [WebKit bug 264473](https://bugs.webkit.org/show_bug.cgi?id=264473); [bugnet guide](https://bugnet.io/blog/how-to-fix-ios-web-game-audio-muted-by-the-silent-switch)
- Older workaround: play a silent looping `<audio>` element to upgrade the page's audio session category so Web Audio ignores the switch — [Audjust](https://www.audjust.com/blog/unmute-web-audio-on-ios); [swevans/unmute](https://github.com/swevans/unmute)
- iOS 17.5.1: Web Audio goes silent after page loses focus; workaround suspend/resume on visibility change — [WebKit bug 276016](https://bugs.webkit.org/show_bug.cgi?id=276016); Web Audio goes silent when another tab that had audio is closed — [WebKit bug 276687](https://bugs.webkit.org/show_bug.cgi?id=276687); transient session types behaved as expected on 17.4 — [WebKit bug 252746](https://bugs.webkit.org/show_bug.cgi?id=252746)

### Inferences
- P11 "Buttons play nothing" on iPhone. Symptom: first button works (or not), later buttons silent; or nothing at all for users with the silent switch on (a large share of iPhone users keep it on). Causes: (a) ambient category + silent switch; (b) context in "suspended"/"interrupted" after app switch, screen lock, or another tab's audio; (c) `resume()` called asynchronously (after an `await`/`setTimeout`) so it is outside the gesture. Detect without device: none of this reproduces in Playwright WebKit or desktop Safari (no ringer switch); only a real iPhone or a cloud real device. Log `ctx.state` and add `ctx.onstatechange` logging to the page and read it via remote Web Inspector. Fix (recommended pattern):
  ```js
  let ctx;
  function getCtx() {
    if (!ctx) {
      const AC = window.AudioContext || window.webkitAudioContext;
      ctx = new AC();
      if (navigator.audioSession) navigator.audioSession.type = 'playback'; // iOS: ignore silent switch
    }
    if (ctx.state !== 'running') ctx.resume(); // call synchronously inside the click handler
    return ctx;
  }
  button.addEventListener('click', () => { const c = getCtx(); playSynth(c); });
  document.addEventListener('visibilitychange', () => {
    if (document.hidden && ctx) ctx.suspend();
  });
  ```
  One shared context for the whole page (iOS also limits the number of live contexts — general knowledge, unverified). Schedule sounds at `ctx.currentTime + 0.01` rather than 0 to absorb resume latency. Whether to bypass the silent switch is a UX choice: a marketing site arguably should respect it; if sounds are core to the demo, set 'playback' only after the user taps a sound toggle.
- `navigator.audioSession` availability: I believe it shipped in Safari 16.4/17 on iOS (general knowledge; could not verify the exact version in this session) — always feature-detect.
- Android Chrome: no "interrupted" state and no ringer-switch muting of Web Audio; autoplay policy still requires a gesture to resume (general knowledge).

### Gaps
- Could not confirm exact Safari version where `navigator.audioSession` shipped, nor whether iOS 18/26 changed the ambient default.
- Status of bugs 273511/276016/276687 in iOS 18/26 unknown.

## 4. Touch and input: click vs pointer events, passive listeners, :active, taps in transformed/3D contexts, elements over canvases

### Takeaway
iOS has documented WebKit bugs where buttons inside nested CSS transforms / 3D (`preserve-3d`, flip cards) do not receive taps because hit-testing does not match the painted position; keep interactive controls out of 3D-transformed subtrees (or overlay them in a flat layer), make tap targets real `<button>`/`<a>`, and keep canvases/decorative overlays at `pointer-events: none`.

### Cited Findings
- WebKit bug 274654 "Transformed button can not be clicked": button with multiple transformed ancestors is not clickable on iOS 17.5.1; reporter suspects visual vs interaction mask mismatch — [WebKit bug 274654](https://bugs.webkit.org/show_bug.cgi?id=274654)
- WebKit bug 258565: regression where taps did not register on 3D-transformed divs (flip cards, buttons on back face); marked fixed but later comment says some cases remain — [WebKit bug 258565](https://bugs.webkit.org/show_bug.cgi?id=258565)
- Older 3D transform issues only on iOS — [Webflow forum](https://discourse.webflow.com/t/3d-transformations-broken-on-only-ios-devices-in-any-browser/22455)
- iOS Safari does not fire `click` on elements it does not consider clickable (div/span) unless they have `cursor: pointer`, an onclick handler, or touch listeners — [tldrdevnotes](https://tldrdevnotes.netlify.com/javascript/events-clicks-taps-mobile-browsers-ios/); tapping on `<body>` does not fire click — [WebKit bug 151933](https://bugs.webkit.org/show_bug.cgi?id=151933); click not fired depending on DOM changes (hover-triggered content) — [WebKit bug 159763](https://bugs.webkit.org/show_bug.cgi?id=159763)
- Apple's Safari Visual Effects guide on interactive control of 3D-transformed content — [Apple Safari guide](https://developer.apple.com/library/safari/documentation/InternetWeb/Conceptual/SafariVisualEffectsProgGuide/InteractiveControl/InteractiveControl.html)

### Inferences
- P12 Dead buttons on/near the 3D phone or in the scaled demo. Symptom: tapping a button inside the CSS-3D phone frame or a transformed card does nothing, or hits the wrong element. Cause: WebKit hit-test mismatch with nested transforms (bugs 274654, 258565); or the WebGL canvas (which copies the phone transform) sits on top and swallows the tap. Detect without device: Playwright WebKit with `hasTouch: true` and `page.tap()` against elements in 3D contexts catches some, not all; in desktop Safari check `document.elementFromPoint(x,y)` at the button centre. Fix: `pointer-events: none` on the WebGL canvas and decorative layers, `pointer-events: auto` only on real controls; keep controls in a flat (non-`preserve-3d`) layer stacked above; if a control must live in a transformed subtree, avoid more than one transformed ancestor and test on device.
- P13 Hover-only affordances. iOS's "first tap triggers hover" behaviour (bug 159763 class) means content revealed on `:hover`/`mouseenter` can require two taps. Gate hover effects behind `@media (hover:hover) and (pointer:fine)` (the site already uses pointer:fine for Lenis).
- P14 Passive listeners (general knowledge, not re-verified): `touchstart`/`touchmove`/`wheel` listeners on window/document are passive by default in Safari and Chrome; any `preventDefault()` in them is ignored with a console warning. Add `{ passive: true }` explicitly on custom listeners and never block scroll in touch handlers; use CSS `touch-action` (e.g. `touch-action: pan-y` on horizontally draggable elements) instead.
- P15 `:active` styles (general knowledge): iOS Safari historically applies `:active` only if a touch listener exists on the element or an ancestor; adding `document.addEventListener('touchstart', () => {}, { passive: true })` restores pressed-state feedback. Also set `-webkit-tap-highlight-color: transparent` with a custom `:active` style so taps still feel acknowledged. Pointer Events are supported in Safari since 13 (general knowledge); prefer `pointerdown`/`click` over `touchstart` for actions; `click` on a `<button>` has no 300 ms delay when the viewport has `width=device-width`.

### Gaps
- Current (iOS 18/26) status of bugs 274654 and 258565 not verified.
- No primary source re-verified in this session for the :active / passive-default claims.

## 5. Fonts, image decoding, large DOM, long tasks; measuring without a device (Web Inspector, Playwright WebKit, BrowserStack)

### Takeaway
Safari decodes `<img>` synchronously by default (except in a few cases), so large webp images entering the viewport during a GSAP film can cause main-thread jank; Safari exposes neither the Long Tasks nor the Long Animation Frames API, so field long-task data from iPhones is unavailable and lab profiling needs Web Inspector from a Mac (Timelines). Playwright WebKit / emulation is good for layout and DPR but not for performance, memory, ringer, Low Power Mode or thermal behaviour.

### Cited Findings
- MDN: Safari defaults `img` decoding to "sync" except in a small number of circumstances; for in-viewport images "async" can flash, "sync" can jank; `decode()` is the usual way to avoid both — [MDN HTMLImageElement.decode()](https://ligm.univ-eiffel.fr/~forax/MDN/developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode.html); [MDN decoding](https://docs.w3cub.com/dom/htmlimageelement/decoding)
- WebKit bug 302801 (Nov 2025): `await img.decode()` caused a crash on iOS Safari in one case — [WebKit bug 302801](https://bugs.webkit.org/show_bug.cgi?id=302801); large 10-bit AVIF failed to render with `decoding="async"` on iOS 16 — [WebKit bug 245668](https://bugs.webkit.org/show_bug.cgi?id=245668)
- Web Performance Calendar 2025: `decode()` still blocked the main thread in Chrome and Safari in their tests; decoding via OffscreenCanvas avoided it — [perfplanet 2025](https://calendar.perfplanet.com/2025/non-blocking-image-canvas/)
- Long Animation Frames API shipped in Chrome/Edge 123; Safari and Firefox not supported; the older `longtask` entry type is also unsupported in Safari — [Chrome developers: LoAF](https://developer.chrome.com/articles/long-animation-frames?authuser=0); [LoAF has shipped](https://developer.chrome.com/blog/loaf-has-shipped?hl=de)
- Web Inspector for iOS requires enabling it on the iPhone and connecting to desktop Safari on a Mac; no official Windows/Linux route — [BrowserStack: Safari remote debugging](https://www.browserstack.com/guide/safari-remote-debugging); [Sizzy](https://sizzy.co/blog/how-to-inspect-element-on-iphone)
- Open-source non-Mac route (ios-webkit-debug-proxy based) lists Timelines events as not working — [ios-safari-remote-debug-kit](https://github.com/HimbeersaftLP/ios-safari-remote-debug-kit)
- Playwright WebKit is not the Safari app: approximates Safari, runs on host CPU, does not reproduce iOS memory pressure, backgrounding, real network or touch performance; layout/DPR/safe areas are "very close" (vendor sources) — [BrowserStack: Playwright iOS](https://www.browserstack.com/guide/playwright-ios-automation); [BrowserStack: Playwright Safari](https://www.browserstack.com/guide/playwright-safari); [qaskills device reference](https://qaskills.sh/blog/playwright-mobile-emulation-devices-reference)
- BrowserStack offers Playwright on real iOS Safari devices — [BrowserStack release note](https://www.browserstack.com/release-notes/en/new-be-among-the-first-to-run-playwright-tests-on-real-ios-safari-browsers-027MSoht)
- Xcode iOS Simulator on a Mac runs real Mobile Safari and can be inspected with Web Inspector — [Soledad Penadés 2024](https://soledadpenades.com/posts/2024/using-simulators-to-test-in-safari)

### Inferences
- P16 Image decode jank during films. Symptom: a hitch when a section with a large webp scrolls in, especially while a film starts at IO threshold. Cause: sync decode on main thread in Safari, plus srcset choosing DPR-3 candidates (very large files) on iPhone. Fix: add `decoding="async"` and `loading="lazy"` to below-the-fold images; cap srcset/`sizes` so iPhones get at most ~2x assets (DPR-3 images are rarely visibly better and cost 2.25x the pixels); pre-decode images used by a film with `img.decode()` before starting the timeline (guard with try/catch given bug 302801); keep hero image `fetchpriority="high"` and not lazy.
- P17 Fonts / FOUT + SplitText (general knowledge, unverified here): on slow mobile networks a webfont swap after SplitText has split the text makes line breaks wrong (lines split with fallback metrics). Fix: start SplitText films after `document.fonts.ready` (or the specific `document.fonts.load('1em Bricolage...')`), preload the 1-2 critical woff2 files, use `font-display: swap` plus a metric-matched fallback (`size-adjust`, `ascent-override`) to cut layout shift. Newer SplitText (GSAP 3.13+, 2025) has `autoSplit`/`onSplit` to re-split on font load/resize — verify in GSAP docs.
- P18 CSS keyframe entrances at first paint: they compete with HTML parsing, font loading and image decode on a slower CPU; on iPhone they may run while the main thread is busy (if they animate non-composited properties) or appear "already finished" if the first frame is late. Animate only `transform`/`opacity`; honour `prefers-reduced-motion`.
- P19 Large DOM from SplitText + chat bubbles + duplicated demo markup increases style/layout cost on every frame of a film; revert splits after films, and keep off-screen films paused (already done).
- Measurement recipe without an iPhone: (1) Playwright WebKit with `devices['iPhone 15']` for layout, tap targets, DPR and srcset choice; (2) Chrome DevTools CPU 4-6x throttle + "Rendering > Frame rendering stats" as a rough proxy for jank and for Android parity; (3) `gsap.ticker.fps(30)` to preview Low Power Mode cadence; (4) in-page instrumentation: a rAF delta logger and `ctx.state` logger that writes to an on-screen debug overlay (works on any phone a tester holds); (5) a cloud real-device service (BrowserStack Live / Automate) for real Safari, but the silent switch, Low Power Mode and thermal behaviour still need a physical device; (6) with a Mac, Web Inspector Timelines (Rendering Frames, JavaScript & Events, Memory) and Layers tab on device or Simulator. The Simulator runs on Mac GPU/CPU so its performance and memory limits are not iPhone-representative.
- Android parity (general knowledge): Chrome on Android does not throttle rAF in Low Power/Battery Saver the same way (it can, on some OEM builds); Chrome throttles cross-origin iframes only when off-screen/hidden, not before first interaction; Chrome supports LoAF for field diagnostics, so Android RUM is a useful proxy for "is a frame long" but not for iOS-specific causes.

- No direct sources retrieved on font loading behaviour specific to iOS Safari (e.g. Safari's 3 s font block period) in 2024-2026.
- No independent benchmarks comparing Playwright WebKit timings to real iPhone Safari timings.
