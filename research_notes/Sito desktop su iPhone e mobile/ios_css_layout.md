# iOS Safari / WebKit CSS and layout pitfalls (iOS 17, 18, 26 era) for a site built and tested in desktop Chromium

Research context: Astro static site; viewport `width=device-width, initial-scale=1, viewport-fit=cover`; fixed header plus fixed bottom sticky CTA using `env(safe-area-inset-bottom)`; `100svh`/`100vh` heroes; CSS 3D iPhone mockups with `preserve-3d` and a WebGL canvas under them; container queries, `:has()`, `backdrop-filter` gated on `(hover:hover)`; variable font Schibsted Grotesk; a transform-scaled live iframe; 2000px box-shadow spotlight inside an `overflow:hidden` rounded phone screen.

Method note: webkit.org, benfrain.com, 1ar.io, nasedk.in and edoardolunardi.dev could not be fetched directly from this environment (DNS/proxy block). Facts from them come from search-engine extracts of those pages, which quote them. Apple Developer Forums pages could be fetched and were read in full. Statements in "Inferences" without a source are my own engineering knowledge and should be verified on a device.

## 1. Viewport units, the dynamic toolbar, fixed/sticky elements, bottom bars and safe areas (incl. iOS 26 Liquid Glass)

### Takeaway
iOS 26 (Safari 26, Liquid Glass) made fixed elements near the bottom edge the riskiest part of this site. The bottom toolbar now floats over the page. Safari will not paint `position:fixed`/`sticky` content below or behind it. Safari 26.0 shipped a "bottom gap" bug for viewport-sized fixed containers, fixed in 26.1, though some people still report it. Safari 26 also tints its own top and bottom bars by sampling fixed elements and the page background, and ignores `theme-color` for this. `100svh` for the hero is the right choice, `100vh` (= `lvh`) is the main source of "content hidden behind toolbar", and `dvh` should not be used for anything that re-lays out on scroll.

### Cited Findings
**Viewport units**
- `svh` = smallest viewport (toolbars expanded); `lvh` = largest viewport (toolbars collapsed), which matches legacy `vh`; `dvh` tracks the live size as the toolbars show and hide. One source says layouts using `dvh` still shift slightly during scroll and should be tested on a real device. — [delightfuldev.com, CSS viewport units guide](https://www.delightfuldev.com/blog/css-viewport-units-guide/)
- When the address bar and bottom toolbar resize during scroll, fixed and sticky elements shift with the changing viewport. — [iifx.dev, Fixing iOS Safari's shifting UI with dvh](https://iifx.dev/en/articles/460170745/fixing-ios-safari-s-shifting-ui-with-dvh)
- A workaround for a fixed-wrapper scroll bug on iOS 16.6 was to size the fixed wrapper with `lvh`. — [GitHub gist nicolaskopp: Fix scrolling bug on iOS Safari with fixed elements and bottom bar](https://gist.github.com/nicolaskopp/637aa4e20c66fe41a6ea2a0773935f6e)
- A common JS fallback sets a CSS variable from `window.innerHeight` and updates it only on orientation change or resize, which avoids jumpy layouts. — [DEV: 100vh problem with iOS Safari](https://dev.to/maciejtrzcinski/100vh-problem-with-ios-safari-3ge9)
- Regression report on iOS 26.0: overlays using `100dvh` left a gap at the bottom, while `100vh` fixed it but broke scrolling on older Safari. The poster said the iOS 26.1 beta did not have the problem. — [Apple Developer Forums 803987: New iOS Safari CSS issue with DVH & VH](https://developer.apple.com/forums/thread/803987)

**iOS 26 (Safari 26) fixed-element bugs**
- In iOS 26 Safari, `position: fixed` and `position: sticky` content is not rendered in the area behind the floating, transparent bottom browser controls; content placed below the visible viewport (repro: fixed `<img>` with `bottom:-100px`) is clipped instead of drawn behind the bar. A user also reports that with the tab bar set to "Bottom" or "Top" (not "Compact"), content no longer scrolls behind the bars, which costs usable space on small phones such as the iPhone SE (2020). The thread dates from September 2025. No Apple reply or fix is visible. — [Apple Developer Forums 800798: iOS 26 Safari will not render position: fixed content below the browser controls](https://developer.apple.com/forums/thread/800798)
- A full-screen fixed element (`inset: 0`, solid background) can leave an uncovered strip at the bottom in Safari 26. The reported workaround was `opacity: 0.99` on the overlay. — [Edoardolunardi.dev: Safari 26 and the strange case of fixed overlays](https://www.edoardolunardi.dev/blog/safari-26-and-the-strange-case-of-fixed-overlays) (via search extract)
- MUI reports the same bottom gap under Drawer and Modal backdrops on iOS 26 in Safari and Chrome, tied to `viewport-fit=cover` and safe-area handling. — [GitHub mui/material-ui #46953](https://github.com/mui/material-ui/issues/46953)
- Safari 26.1 release notes list a Rendering fix for "a bottom gap on layouts with viewport-sized fixed containers" on iOS (tracking ID 158055568). One forum commenter confirmed it on the 26.1 beta. — [WebKit Features for Safari 26.1](https://webkit.org/blog/17541/webkit-features-for-safari-26-1/); [Apple Developer Forums 799216](https://developer.apple.com/forums/thread/799216)
- Reports conflict on whether 26.1 fully fixed it. One PR says the gap "still shows on that phone" after 26.1 and works around it with an empty fixed "probe" element that measures the usable height. Another issue notes a similar symptom on iOS 26.6.2 with an unclear cause. — [GitHub viliket/pure-web-bottom-sheet PR #53](https://github.com/viliket/pure-web-bottom-sheet/pull/53); [GitHub MLGalusha/letter-archive #172](https://github.com/MLGalusha/letter-archive/issues/172); [GitHub CostardRouge/atelier PR #236 "Safari 26's empty band under the bottom menu"](https://github.com/CostardRouge/atelier/pull/236)
- A `bottom: 0` fixed nav bar no longer sits at the bottom after the on-screen keyboard is dismissed (iOS 26 report). — [Apple Developer Forums 800154](https://developer.apple.com/forums/thread/800154)
- iOS 26 beta: keyboard toolbar mispositioned with the bottom safe-area inset. — [Apple Developer Forums 798598](https://developer.apple.com/forums/thread/798598)
- Practitioner write-up "[FIX] iOS 26 Safari: web layouts are breaking due to fixed/sticky position elements getting misplaced". — [Pratik Pathak](https://pratikpathak.com/fix-ios-26-safari-web-layouts-are-breaking-due-to-fixed-sticky-position-elements-getting-misplaced/)

**iOS 26 toolbar tinting (affects the fixed header's look)**
- Safari 26 samples the page to tint its status bar and bottom bars, falls back to white where it finds nothing to sample, and ignores `<meta name="theme-color">` for Liquid Glass tinting. — [1ar.io: Safari 26 Liquid Glass: toolbar tinting, white bars, viewport bugs](https://1ar.io/updates/safari-26-liquid-glass-web/) (via search extract)
- The toolbar colour comes either from the body background or from a `position:fixed` element at the very top of the page with a `background-color`. Another report says Safari tints from a fixed or sticky element that reaches the viewport edge, and falls back to the root background when there is none. — [grooovinger: Define the theme color for Safari 26](https://grooovinger.com/notes/2026-02-27-safari-26-header-background); [Ben Nasedkin: Safari 26–27 colors](https://nasedk.in/blog/ios26-safari-toolbar-colors/)
- A fixed element parked at `opacity: 0` still tinted the toolbar, so the developer unmounted it instead. Advice from that guide: don't put `background-color` or `backdrop-filter` on the fixed or sticky element itself; put the visual background on an absolutely positioned child. Also set an explicit, non-transparent `background-color` on both `html` and `body`. — [Ben Nasedkin](https://nasedk.in/blog/ios26-safari-toolbar-colors/); [Huxpro/hux.pro PR #92 "Fix iOS 26 Safari Liquid Glass viewport tinting"](https://github.com/Huxpro/hux.pro/pull/92); [thatdevpro: meta theme-color iOS 26 fix](https://www.thatdevpro.com/reference/html-meta-theme-color/)
- Safari's tab tint can take the background colour of a fixed element, which looks wrong with fixed-position elements. A WebKit bug about it was closed as a duplicate. — [Ben Frain: iOS26 Safari theme-color/tab-tinting with fixed position elements is a mess](https://benfrain.com/ios26-safari-theme-color-tab-tinting-with-fixed-position-elements/) (via search extract)
- Users can turn tinting off in Settings > Safari > Tabs > "Allow Website Tinting". — [1ar.io](https://1ar.io/updates/safari-26-liquid-glass-web/) / [andesco/safari-color-tinting](https://github.com/andesco/safari-color-tinting)
- Apple forum thread on toolbar tint colour with Liquid Glass. — [Apple Developer Forums 798031](https://developer.apple.com/forums/thread/798031)

**Safe-area insets and bottom CTA bars**
- Pattern: put the inset in padding, e.g. `padding-bottom: calc(1rem + env(safe-area-inset-bottom, 0px))`, or offset with `bottom: env(safe-area-inset-bottom, 0px)`. The home-indicator inset is about 34px on Face ID iPhones. — [Medium: Understanding CSS env()](https://medium.com/@tharunbalaji110/understanding-css-env-function-a-developers-guide-to-safe-areas-80bcaabcb435); [Mironsoft: safe-area insets, notch and Dynamic Island](https://www.mironsoft.de/en/blog/css-safe-area-insets-iphone-notch-dynamic-island); [Polypane: Using safe-area-inset](https://polypane.app/blog/using-safe-area-inset-to-build-mobile-safe-layouts/)
- History: with iOS 15's bottom tab bar, fixed footers had tap-target problems and the bar overlapped fixed bottom UI. Older threads report `env(safe-area-inset-*)` returning 0px in portrait. In portrait, left and right insets are legitimately 0; only top and bottom are non-zero. — [Samuel Kraft: Using bottom tab bars on Safari iOS 15](https://samuelkraft.com/blog/safari-15-bottom-tab-bars-web); [Apple Forums 685481](https://developer.apple.com/forums/thread/685481); [Apple Forums 699415](https://developer.apple.com/forums/thread/699415); [Apple Forums 717296](https://developer.apple.com/forums/thread/717296)
- One low-quality source suggests `calc(20px + env(safe-area-inset-bottom))` on floating buttons so they clear the iOS 26 floating bar. The numbers are unverified. — [iifx.dev: safe-area insets and z-index on the new iOS Safari](https://iifx.dev/en/articles/460245553/safe-area-insets-and-z-index-debugging-modals-on-the-new-ios-safari)

### Inferences
- **Hero (`min-height: calc(100svh - header)`).** This is correct, and it is the most robust unit for an above-the-fold hero: it never sits under the expanded toolbar and does not re-lay out on scroll. Keep it. Fallback order: `min-height: calc(100vh - var(--header)); min-height: calc(100svh - var(--header));`. `svh` is supported since Safari/iOS 15.4, so the fallback only matters for very old devices.
- **The 9 uses of `100vh`.** Audit each one. On iOS `100vh` equals `100lvh`, so a `100vh` box is taller than the visible area while the toolbar is expanded: its bottom content (a CTA, a "scroll" cue, a centred element's lower half) sits under the toolbar on first load. Replace with `100svh` for "fit on first screen" blocks. Use `100lvh` only for backgrounds that must never show a gap when the toolbar collapses. Never use `dvh` on large in-flow sections: it re-lays out the page on every toolbar show/hide, causing jumps and scroll-anchoring shifts.
- **Bottom sticky CTA bar on iOS 26.** Safari 26 no longer lets fixed content render behind the floating bar, so a CTA with `bottom:0` sits directly above the bar. Recommended CSS: `position:fixed; left:0; right:0; bottom:0; padding: 12px max(16px, env(safe-area-inset-left)) calc(12px + env(safe-area-inset-bottom, 0px)) max(16px, env(safe-area-inset-right));`. Do not use negative `bottom` values or try to bleed under the bar; that content is clipped (Forums 800798). Give the CTA bar a solid, opaque background equal to the page or brand colour. Safari 26 will likely sample it for the bottom toolbar tint, so a semi-transparent or blurred CTA bar can produce an odd tint. Hide the CTA while a text input is focused (`focusin`/`focusout`), to avoid the post-keyboard mispositioning (Forums 800154).
- **Fixed header.** In Safari 26 a fixed header with a `background-color` at the top edge becomes the status-bar and toolbar tint source. If the header is transparent over a dark hero and then turns solid, the tint will flip. Set `html, body { background-color: <page colour> }` explicitly. Optionally move the header background to an absolutely positioned `::before` child, per the Nasedkin and grooovinger advice. If the header hides on scroll via `transform: translateY(-100%)`, unmount or `visibility:hidden` it rather than relying on `opacity:0`, which still tints.
- **Landscape.** `viewport-fit=cover` means the notch or Dynamic Island side gets `safe-area-inset-left`/`right` (about 47–62px) in landscape. Every full-bleed fixed bar and the hero padding need `padding-inline: max(16px, env(safe-area-inset-left))`, or text and buttons sit under the notch.
- **Full-screen fixed overlays on iOS 26.0.** For menu overlays or modals with `inset:0`, add `opacity: .99` (community fix), or size with `height: 100lvh` instead of `bottom:0`/`100dvh`, to avoid the 26.0 bottom band. Re-test on 26.1+.
- **Detecting without a device.** Xcode's iOS Simulator (macOS only) reproduces the toolbar and Liquid Glass behaviour reasonably well. Playwright's WebKit on Linux and Chrome DevTools device mode do NOT emulate the dynamic toolbar, `svh`≠`lvh`, safe areas or Safari 26 tinting. In DevTools you can only sanity-check by setting a 390×664 viewport (iPhone 15/16 visible height with expanded bars) and checking that every `100vh` block's important content fits.

### Gaps
- No Apple or WebKit statement documents the exact Safari 26 toolbar-tint sampling rules. Everything above is community reverse-engineering.
- No authoritative value is known for `env(safe-area-inset-bottom)` under the iOS 26 floating compact tab bar, i.e. whether it still reports about 34px or changes with bar state. Needs device testing.
- It is unclear whether "fixed content not rendered behind bottom controls" (Forums 800798) has been addressed in 26.2–26.5. No release note found.

## 2. Touch interaction and typography: sticky :hover, tap highlight, double-tap / 300ms, input focus zoom, text inflation, font rendering, text-wrap

### Takeaway
On iOS, `:hover` rules outside `(hover:hover)` fire on tap and "stick" until the user taps elsewhere. If a hover rule shows or hides content, the first tap can be swallowed as a hover, so the user has to tap twice. Inputs under 16px trigger focus zoom; this site's 18px inputs are safe. `-webkit-font-smoothing` has no effect on iOS, so text looks heavier and wider than in a desktop mockup. `text-wrap: balance` works from Safari 17.5 and `pretty` from Safari 26.

### Cited Findings
- Safari on iOS treats a tap as hover first, then click. If a `:hover` rule hides or shows another element using `visibility` or `display`, the first tap only triggers hover, so a second tap is needed. Plain colour changes don't trigger this. A later update says `::after` reveals no longer required a double tap on iOS 13. Recommended fix: scope hover styles to `@media (hover: hover)` or neutralise them under `(hover: none)`, and replace mouseover/mouseenter JS with click. — [Nicholas Zakas: iOS has a :hover problem](https://humanwhocodes.com/blog/2012/07/05/ios-has-a-hover-problem/); [CSS-Tricks](https://css-tricks.com/?p=246048); [Shopify community: iOS double tap for hover effects](https://community.shopify.com/t/how-can-i-fix-the-ios-double-tap-problem-for-hover-effects/193223)
- Some double-tap reports were caused by JS libraries hijacking click and tap events rather than CSS. — [Drupal.org #2564725](https://www.drupal.org/node/2564725); [GeneratePress forum](https://generatepress.com/forums/topic/what-causes-the-ios-button-click-behaviour-to-need-a-double-tap-sometimes/)
- Controls gated behind hover (`opacity:0; pointer-events:none` until hovered) are unreachable on touch, because hover never becomes true. — [GitHub kahme247/ompweb #87](https://github.com/kahme247/ompweb/issues/87)
- iOS Safari zooms into an input whose rendered font size is under 16px, and doesn't zoom back out on blur. Fix: a minimum of 16px on form controls on mobile. Don't disable zoom via `maximum-scale`/`user-scalable=no`. — [Defensive CSS: Input zoom on iOS Safari](https://defensivecss.dev/tip/input-zoom-safari/); [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines); [Rick Strahl: Preventing iOS textbox auto zooming](https://weblog.west-wind.com/posts/2023/Apr/17/Preventing-iOS-Textbox-Auto-Zooming-and-ViewPort-Sizing); [heroui #5326](https://github.com/heroui-inc/heroui/issues/5326)
- Reports conflict on whether `touch-action: manipulation` affects the input auto-zoom, and one commenter said a trick stopped working in iOS 14.6. Treat `touch-action` as unreliable for focus zoom. — [DEV: Disabling viewport zoom on iOS 14 web browsers](https://dev.to/jasperreddin/disabling-viewport-zoom-on-ios-14-web-browsers-l13)
- Font weight looks different between Chrome and Safari partly because of `-webkit-font-smoothing`, which is rendered differently. Setting it to `antialiased` made text lighter on macOS. A Safari mobile user saw heavier weights than on desktop. A missing weight (e.g. using 600 when only 400 is loaded) makes the browser synthesize bold differently in Safari. — [Themeco forum: font weights and letter spacing off on iOS](https://theme.co/forum/t/font-weights-and-letter-spacing-way-off-on-ios-safari-and-chrome/70670); [Themeco: font weight different on devices](https://theme.co/forum/t/font-weight-different-on-different-devices-and-browsers/9355); [Webflow: font weight gets lighter on Safari](https://discourse.webflow.com/t/font-weight-gets-lighter-on-safari/4892)
- `text-wrap: balance` has been supported unprefixed since Safari 17.5 (caniuse: unsupported up to 17.4, supported 17.5–26.x), with no line-count limit in WebKit (Chromium caps balancing at a few lines). — [caniuse: text-wrap balance](https://caniuse.com/css-text-wrap-balance); [WebKit Features in Safari 17.5](https://webkit.org/blog/15383/webkit-features-in-safari-17-5/)
- `text-wrap: pretty` landed in Safari Technology Preview 215–216 (April 2025) and shipped in Safari 26. WebKit's implementation adjusts all lines of a paragraph (rag, hyphenation, short last lines), not only the last few lines as in Chromium. — [WebKit WWDC25: News from WWDC25, Safari 26 beta](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/); [STP 216 release notes](https://webkit.org/blog/16731/release-notes-for-safari-technology-preview-216); [Daring Fireball](https://daringfireball.net/2025/04/webkit_textwrap_pretty); [CSS-Tricks: Touring new CSS features in Safari 26](https://css-tricks.com/touring-new-css-features-in-safari-26/)

### Inferences
- **The 23 `:hover` rules outside `@media (hover:hover)` are the top "looks broken on iPhone" item in this section.** On tap, the hover state (lift, shadow, colour, underline, scale) applies and stays until another element is tapped, so cards look "stuck" in hover. Any rule that reveals content (`display`/`visibility`/`opacity` + `pointer-events`) can cause double-tap. Fix: wrap every decorative hover in `@media (hover: hover) and (pointer: fine) { … }`, and give touch an equivalent `:active` style (`:active` needs a touch listener on iOS; `document.addEventListener('touchstart', ()=>{}, {passive:true})` is the classic enabler). Use `:focus-visible` for keyboard users.
- **Tap highlight.** iOS draws a translucent grey/blue rectangle on tapped links and buttons, ignoring `border-radius` on older versions. Set `-webkit-tap-highlight-color: transparent` on `a, button, label, [role=button]` and provide your own `:active` feedback. This matters for the custom radio "cards" (a `label` wrapping the input), which otherwise flash a grey rectangle over a rounded card.
- **300ms delay / double-tap zoom.** With `width=device-width` there has been no 300ms click delay since iOS 9.3 (WebKit "More responsive tapping on iOS", 2016). Double-tap-to-zoom can still trigger on quick repeated taps (e.g. on a 3D tilt or stepper). Add `touch-action: manipulation` to interactive controls and the 3D mockup to suppress double-tap zoom while keeping pinch zoom.
- **Input focus zoom.** The 18px inputs are safe. Check `select`, `textarea` and any search or newsletter input in the footer or demo, plus any rule that scales inputs down via `font-size: .875em` or `clamp()` resolving below 16px at 320–375px widths.
- **Text inflation in landscape.** `-webkit-text-size-adjust: 100%` on `html` is correct and prevents iOS from inflating text on rotation. Do not use `none`, which also blocks user zoom of text in some cases. Add unprefixed `text-size-adjust: 100%` for Chromium; Safari only honours the prefixed one.
- **`-webkit-font-smoothing: antialiased` only affects macOS.** iOS always uses its own greyscale antialiasing, so headings at weight 700–800 with negative letter-spacing look heavier and tighter on iPhone than on a laptop where `antialiased` thins them. Mitigations: test heading tracking at real size; reduce negative letter-spacing on small screens (e.g. `letter-spacing: clamp(-0.03em, -0.5vw, -0.01em)`, or `-0.01em` under 480px); consider weight 700 instead of 800 on mobile headings.
- **Variable font.** Make sure `@font-face` declares `font-weight: 400 900` (a range). Otherwise WebKit may treat the face as a single weight and synthesize bold for 600–800, which gives smeared, wider glyphs. Add `font-synthesis: none` (or `font-synthesis-weight: none`, supported in Safari 16.4+) to catch this. Preload the woff2 so the metric-override fallback swap is brief. Safari supports `size-adjust`/`ascent-override` since Safari 17, so the metric-override fallback works on iOS 17+.
- **Detecting without a device.** Playwright's WebKit build (Linux) renders `text-wrap`, hover-media and font-synthesis behaviour close enough for screenshots. Emulate touch with `hasTouch: true, isMobile: true` to check that `(hover:hover)` is false. It does not reproduce iOS glyph rasterisation.

### Gaps
- No primary source found for current (iOS 17–26) sticky-hover behaviour details, e.g. whether `:hover` clears on scroll. The CSS-Tricks and Zakas material is older.
- No primary source on the -webkit-tap-highlight-color default in iOS 17–26.
- No iOS-specific source confirming `-webkit-font-smoothing` is a no-op on iOS (widely known; MDN states it is macOS-only, not fetched here).

## 3. 3D transforms, compositing, clipping and effects: preserve-3d flattening, backface, flicker, layer memory, fixed inside transforms, overflow+radius clipping, big shadows, container queries, :has, backdrop-filter

### Takeaway
Most "the iPhone mockup looks flat, clipped or flickers" problems come from properties that by spec force flattening of a `preserve-3d` subtree: `overflow` other than visible, `opacity < 1`, `filter`, `clip-path`/`mask`, `isolation`. WebKit enforces these strictly. Keep those properties off every element between the `perspective` root and the 3D faces, and apply them on wrappers outside the 3D context. Rounded `overflow:hidden` screens holding transformed or composited children (the scaled iframe, the WebGL canvas, the 2000px box-shadow spotlight) are a long-standing WebKit clipping weak spot. Force a stacking or compositing layer or a mask on the clipping element. Container queries (Safari 16.0+) and `:has()` are safe on all realistic iOS versions. `backdrop-filter` still needs the `-webkit-` prefix in practice.

### Cited Findings
- WebKit: clipping requires flattening, so a non-visible `overflow` overrides `transform-style: preserve-3d`. A 2010 report was closed as expected behaviour, and a later WebKit change disabled preserve-3d on elements with flattening-forcing styles (overflow, filters). — [WebKit Bugzilla 43958](https://bugs.webkit.org/show_bug.cgi?id=43958); [WebKit Bugzilla 48386](https://bugs.webkit.org/show_bug.cgi?id=48386); [WebKit Bugzilla 83337](https://auto-bugs.webkit.org/show_bug.cgi?id=83337)
- The CSS Transforms spec lists opacity < 1 among properties requiring a flattened representation, overriding preserve-3d. When Chrome 53 started flattening on opacity, a Safari engineer said Safari's flattening was correct ("there's no way you can do group opacity in this model without rendering some subtree … into a texture"). — [WICG discourse: Chrome 53 breaks CSS3D with opacity flattening](https://discourse.wicg.io/t/chrome-53-breaks-css3d-with-opacity-flattening/1694); [W3C public-fx, Rik Cabanier 2016](https://lists.w3.org/Archives/Public/public-fx/2016JulSep/0013.html); [W3C bug 19612: other properties that cause flattening](https://lists.w3.org/Archives/Public/public-css-bugzilla/2012Oct/0044.html)
- An element could disappear when preserve-3d + opacity < 1 + `backface-visibility: hidden` were combined (Firefox report; removing any one restored it). — [Mozilla bug 1109236](https://bugzilla.mozilla.org/show_bug.cgi?id=1109236)
- `backface-visibility` handling has differed between engines in nested 3D contexts (test green in Firefox, red in Chrome and Safari); the spec was judged underdefined. — [W3C bug 16349](https://www.w3.org/Bugs/Public/show_bug.cgi?id=16349)
- Flicker during CSS transitions on iOS was removed by setting `backface-visibility: hidden` on animated elements and their images. Apple's guide: hiding the back face stops the mirrored front face showing. — [pixeldock: avoid flickering with CSS transitions in iOS](https://www.pixeldock.com/blog/how-to-avoid-the-ugly-flickering-effect-when-using-css-transitions-in-ios/); [Apple Safari Visual Effects Guide: Using 2D and 3D transforms](https://developer.apple.com/library/archive/documentation/InternetWeb/Conceptual/SafariVisualEffectsProgGuide/Using2Dand3DTransforms/Using2Dand3DTransforms.html)
- Resizing an on-screen WebGL canvas in iOS Safari leaked memory on each resize until the tab was killed at about 1.25 GB (WebKit bug 219780 / rdar://72464396). 2D canvases were unaffected. Reported fixed in iOS 14.3. — [WebKit Bugzilla 219780](https://bugs.webkit.org/show_bug.cgi?id=219780); [Apple Developer Forums 668999](https://developer.apple.com/forums/thread/668999)
- `border-radius` + `overflow:hidden` failing to clip composited or transformed children is a long-standing WebKit bug (duplicate report 98538 for 2D/3D-transformed children). The underlying bug (68196) was reportedly marked fixed in September 2022 (STP 156), but newer reports (254151) show related iOS inconsistencies. Community workarounds on the clipping element: `isolation`/`z-index` + `position:relative`; `transform: translateZ(0)`; `will-change: transform`; or `-webkit-mask-image: -webkit-radial-gradient(white, black)` / `mask-image: radial-gradient(white, black)`. Tested on iOS 14.4 and reported working on iOS 16. — [GitHub gist domske](https://gist.github.com/domske/b66047671c780a238b51c51ffde8d3a0); [WebKit Bugzilla 98538](https://bugs.webkit.org/show_bug.cgi?id=98538); [WebKit Bugzilla 254151](https://bugs.webkit.org/show_bug.cgi?id=254151); [Jianshu analysis](https://www.jianshu.com/p/687779212eef); [Medium kes3583](https://medium.com/@kes3583/safari-bug-border-radius-overflow-hidden-c2a09f40ad89)
- Size container queries and container query units (`cqw`, `cqi`…) have been supported since Safari/iOS 16.0. caniuse lists iOS 3.2–15.8 unsupported and 16.0–26.x supported. — [caniuse: container query units](https://caniuse.com/css-container-query-units); [caniuse mdn cq length units](https://caniuse.com/mdn-css_types_length_container_query_length_units); [Chrome Developers: container queries land in stable browsers](https://developer.chrome.com/blog/cq-polyfill)
- `backdrop-filter`: an MDN compat issue (tested on Safari 18.3) says Safari 18 still needs the `-webkit-` prefix, and that `-webkit-backdrop-filter` does not accept CSS custom properties, only literal values. — [mdn/browser-compat-data #25914](https://github.com/mdn/browser-compat-data/issues/25914). (MDN data at the time claimed unprefixed support in Safari 18; this is the conflict the issue raises.)
- Safari 26.0 shipped scroll-driven animations and CSS anchor positioning. Safari 26.5 lists four reliability fixes for scroll-driven animations. — [WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/); [WebKit Features for Safari 26.5](https://webkit.org/blog/17938/webkit-features-for-safari-26-5/); [WebKit Features for Safari 26.2](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/)

### Inferences (applied to this site)
- **The rotateY 360° phone turn.** Check every ancestor between the element with `perspective` and the faces (front, back, sides). If any has `overflow: hidden|clip`, `opacity<1` (including mid-fade-in from a reveal animation), `filter`, `mask`, `clip-path`, `contain: paint`, or `isolation: isolate`, WebKit flattens it. The phone then turns as a flat card, the back face shows mirrored, or sides vanish. This applies to the `overflow-x: clip` on sections too, if the section itself is the `transform-style: preserve-3d` element or sits between the perspective root and the faces. Fix: put the reveal opacity, clip and drop-shadow on an outer wrapper; make the inner stage `transform-style: preserve-3d` with no clipping or effects. `overflow: clip` on an ancestor *above* the perspective root is fine.
- **Backface.** Put `backface-visibility: hidden` plus `-webkit-backface-visibility: hidden` on each face, and offset the back face by `rotateY(180deg) translateZ(thickness)` rather than leaving faces coplanar. Coplanar faces (e.g. screen and glass at the same Z) z-fight and flicker in WebKit during rotation. Separate them by at least 0.5–1px in `translateZ`.
- **WebGL canvas under the HTML screen, copying the CSS 3D transform.** In WebKit the canvas and the HTML screen are separate composited layers. Any rounding difference in the matrix makes the HTML screen and the canvas drift by a pixel or z-fight during the turn. Put both inside the same `preserve-3d` parent and apply the transform once to the parent, rather than duplicating the matrix in JS. Size the canvas once, not on every scroll or resize: toolbar show/hide fires `resize` on iOS, and WebGL resize was historically a memory leak (bug 219780, fixed 14.3). Cap `devicePixelRatio` at 2 (iPhones are 3×), and lose the context (`WEBGL_lose_context`) when the mockup is off-screen. iOS kills tabs that exceed memory (roughly 1–1.5 GB) with a "This webpage was reloaded because a problem occurred" message.
- **`filter: drop-shadow` on the canvas.** Disabling it on coarse pointers is right. Besides the cost, `filter` forces flattening. If the canvas is inside the 3D context this flattens it, so use a pre-blurred PNG or a `box-shadow` on a non-3D wrapper.
- **Tilt on pointer.** Updating `transform` on `pointermove` is cheap, but on iOS there is no hover pointer, and `pointermove` only fires during a touch drag, which competes with page scroll. Disable tilt under `(hover:none)` or `(pointer:coarse)`, or use `touch-action: pan-y` on the mockup, so vertical scroll isn't hijacked.
- **The 2000px box-shadow "spotlight" inside an overflow:hidden rounded phone screen.** This combines the two weakest WebKit spots. (a) The shadow paints a huge rect (≈4000×4000 px at 3× DPR, about 64 MB of backing store if it becomes its own layer). (b) Clipping it to a rounded, transformed parent may leak past the radius (bug 68196/98538 family), especially while the phone is animating. Fix: add `isolation:isolate; -webkit-mask-image: -webkit-radial-gradient(white, black);` (or `transform: translateZ(0)`) on the screen element. Better, replace the shadow trick with a `radial-gradient` overlay or an SVG/`mask` cut-out on a pseudo-element the size of the screen, and animate its position with a custom property. Note this screen is likely *inside* the 3D phone, so applying a mask there flattens only the screen subtree, which is fine as long as the screen is a single face.
- **`position:fixed` inside a transformed ancestor.** By spec, any `transform`, `perspective`, `filter`, `will-change: transform` or `contain: paint` on an ancestor makes it the containing block for fixed descendants. A fixed modal, toast or CTA rendered inside the 3D mockup or a transformed section scrolls with that ancestor instead of the viewport, in all engines. iOS makes it more visible because the "fixed" element then also ignores safe areas. Keep fixed UI as direct children of `body` (Astro: render it in the layout, not inside the component).
- **`overflow-x: clip` on sections.** This is supported since Safari 16; on iOS 15 it falls back to visible, so add `overflow-x: hidden` before it as a fallback. Unlike `hidden`, `clip` does not create a scroll container, so `position: sticky` children keep working. Prefer it over `hidden` on any ancestor of a sticky element.
- **Container queries / `cqw`.** Safe on iOS 16+. Pitfall: an element with `container-type: inline-size` gets size containment on the inline axis, so a phone frame whose width comes from its contents (`width: fit-content`, inline-flex, grid `auto` track) collapses to 0 width on iOS just as in Chrome. If the screen looks tiny or blank on iPhone only, check that the container has a definite width at mobile breakpoints. `cqw` inside a 3D-transformed container resolves against the untransformed size, which is expected.
- **`:has()`.** Supported since Safari 15.4 (iOS 15.4, March 2022), so the custom radio cards using `:has(input:checked)` are fine on every iOS that also supports container queries. If iOS < 15.4 matters, add a fallback with `input:checked + .card` sibling structure.
- **`backdrop-filter`.** Always ship `-webkit-backdrop-filter` with literal values next to the unprefixed one. Scoping it to `(hover:hover)` means iPhones never get it; make sure the non-blurred fallback background is opaque enough (e.g. `rgba(…, .92)`) or the header text becomes unreadable over the hero on iOS.
- **Detecting without a device.** Playwright WebKit on Linux enforces the same flattening rules, so a screenshot mid-rotation will show flattened faces. Chrome also flattens on overflow and opacity, so the bug may be visible in Chrome too if you look mid-animation. Layer and memory problems need Safari Web Inspector > Layers on a Mac with a tethered iPhone or the Simulator.

### Gaps
- No 2024–2026 WebKit source specifically on z-fighting or flicker of CSS 3D mockups on iOS 17–26. The cited evidence is older (2012–2021).
- No measurement found of the GPU or memory cost of very large `box-shadow` spreads on iOS. The 64 MB figure is my own arithmetic, assuming 4 bytes/px.
- `:has()` (Safari 15.4) and `overflow: clip` (Safari 16) versions are from my knowledge; the search did not return a caniuse page for them.
- Whether Safari 26.x finally supports unprefixed `backdrop-filter` with custom properties was not confirmed.

## 4. iframes on iOS (scaling, scrolling, height), scroll anchoring, overscroll/rubber-band, smooth scroll

### Takeaway
The old iOS iframe "frame flattening" (iframes auto-expanding to their content height and not scrolling) was turned off in Safari 13 (iOS 13). Modern iOS iframes respect their width and height and scroll internally with one finger. A transform-scaled iframe still has gotchas: its layout box stays unscaled, the inner page sees the unscaled width, touch scrolling inside a scaled iframe moves at the scaled rate, and content with horizontal overflow can widen the iframe.

### Cited Findings
- Historically iOS expanded iframes to full content height and ignored `scrolling="yes"`, to avoid nested scroll traps on small screens. Bug 149264 was filed in 2015. — [WebKit Bugzilla 149264](https://bugs.webkit.org/show_bug.cgi?id=149264)
- Safari 13 release notes: "Disabled frame flattening on iOS"; frames now render as on desktop, and all frames and scrollable overflow areas use accelerated one-finger scrolling. — [Safari 13 release notes (Apple)](https://developer.apple.com/tutorials/data/documentation/safari-release-notes/safari-13-release-notes.md); [WebKit Bugzilla 204045](https://bugs.webkit.org/show_bug.cgi?id=204045)
- Older workarounds include JS that sets iframe width and height to the container size on load and resize; `scrolling="no"` (iOS 4–5 era); and `width:1px; min-width:100%` when iframe content has horizontal scroll areas that make the iframe expand. — [GitHub gist stephenparish: Embedded iframe resizing](https://gist.github.com/stephenparish/4f6f01f0ff2113f094e4f366087f1420); [salomvary: iframes automagically fit their content on iOS](https://salomvary.com/iframe-resize-ios-safari.html); [DevGex: responsive iframes in iOS Safari](https://devgex.com/en/article/00027824)
- A CSS transform shrinks rendering, but the element still takes up its original CSS size in layout, so position and size must be compensated manually. An Apple forum thread describes an iframe that reverts to its desktop size after load on iOS. — [Apple Developer Forums 100467: iframe scale problem](https://developer.apple.com/forums/thread/100467); [Adobe community thread](https://community.adobe.com/questions-621/shrink-the-content-of-an-iframe-to-appear-without-scroll-bars-648598)

### Inferences
- **Scaled demo iframe.** Give the iframe its *intended* CSS size (390×844 or 1280×800) explicitly, scale with `transform: scale(var(--s)); transform-origin: 0 0`, and wrap it in a box of the *scaled* size with `overflow:hidden` (same rounded-clip caveats as section 3). Compute `--s` from the container's measured width, ideally via `cqw`: `--s: calc(100cqw / 390px)` is invalid (unit division isn't supported cross-browser), so set it in JS on `ResizeObserver` instead. The demo page inside must have its own `<meta name="viewport" content="width=device-width">`; otherwise WebKit lays out the iframe document at 980px.
- **The 1280px "desktop" mode** scaled to about 0.27 on a 350px phone screen gives text roughly 4px tall (unverified: the iframe document's own text-size-adjust, not the parent's, would govern any inflation), so the result looks like a thumbnail. On iPhone, show a static screenshot for the desktop view, or allow a tap to open the demo full-screen.
- **Touch scrolling inside a scaled iframe.** iOS scrolls the iframe in its own (unscaled) coordinates, so a 1-finger swipe moves the content about 1/scale faster, and the iframe can capture the page's vertical scroll (scroll trap). Consider `pointer-events:none` on the iframe on coarse pointers, plus an explicit "Scroll the demo" toggle; or `overscroll-behavior: contain` inside the demo page (supported since Safari 16) so reaching the end doesn't chain-scroll the parent awkwardly.
- **Rubber-band and overscroll.** iOS rubber-band reveals the `html` background above and below the page. Set `html { background: <header colour> }` and `body { background: <page colour> }`, otherwise a white band appears on pull-down. This also feeds Safari 26 toolbar tinting. `overscroll-behavior-y: none` on `html` disables bounce on Safari 16+, but also removes the native feel. Prefer setting colours.
- **Smooth scroll.** `scroll-behavior: smooth` has been supported since Safari 15.4. Wrap it in `@media (prefers-reduced-motion: no-preference)`. Use `scroll-margin-top: calc(var(--header) + env(safe-area-inset-top))` on anchors so the fixed header doesn't cover targets.
- **Scroll anchoring.** Safari has historically not implemented CSS scroll anchoring (`overflow-anchor`); WebKit work on it was in progress, so verify current status on caniuse. When content above the viewport changes height (font swap, lazy images without dimensions, `dvh` sections resizing with the toolbar), iOS jumps visibly where Chrome compensates. Always set `width`/`height` or `aspect-ratio` on images and iframes. Keep the font fallback metric-matched (already done). Avoid `dvh` on in-flow sections.
- **Detecting without a device.** Playwright WebKit can verify iframe sizing and scale maths. Chrome DevTools will *hide* the scroll-anchoring difference because Chrome has anchoring.
